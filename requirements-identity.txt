# torch/torchvision: a plain `torch>=2.0.0` resolves to the latest PyPI
# wheel, which bundles its own CUDA 13.x runtime — VERIFIED FAILING on
# serra1 (2026-09-24): pip started downloading torch==2.14.0 +
# nvidia_cudnn_cu13/nvidia_nccl_cu13, hundreds of MB in, before this was
# caught and killed. serra1's driver caps at CUDA 12.5 (same constraint
# lose-the-faces-keep-the-lesson's own pyproject.toml already documents for
# its own torch/onnxruntime-gpu deps) — redirected to PyTorch's own cu124
# wheel index instead, pinned to the EXACT versions already verified
# working for that project's phase2-ganonymization extra
# (torch==2.6.0+cu124/torchvision==0.21.0+cu124, confirmed initializing
# CUDA and running real inference on this same machine).
# torchaudio: NOT a direct dependency of anything this backend actually
# uses (no audio anywhere in this pipeline) — but VERIFIED (2026-09-24)
# that `transformers` eagerly imports it via a transitive chain
# (transformers.audio_utils, reached through its CLIP image-processor
# import path, imported even for pure-vision use) whenever it's installed
# at all, and pip resolved an unpinned `torchaudio==2.11.0` (its own latest,
# CUDA-13-targeted `libcudart.so.13`) since nothing here constrained it —
# broke the exact same way the unpinned torch/torchvision did before this
# file's earlier fix. Pinned to the version actually released alongside
# torch 2.6.0, through the same cu124 index.
